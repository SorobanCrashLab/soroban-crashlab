# Game day 2026-10-16: KV / Redis down

- **Playbook:** [KV / Redis down](../playbooks/kv-down.md)
- **Format:** live fault injection on the reference deployment
  (`deploy/compose`, `CRASHLAB_TLS_MODE=internal`, local host), IC + ops lead
  roles taken by one engineer.
- **Fault:** `docker compose stop redis`, with the app serving traffic.

Detection-to-recovery in the drill: about 1 minute once the symptom was
seen; restart-to-healthy 16 s. No data written before the fault was lost
(Redis reloaded `dump.rdb`).

## What the playbook got wrong (fixed in the same PR)

- It assumed `/api/health` would show KV failures. It does not: the health
  route checks the database, Prometheus and integrations, not KV. The
  playbook now says so and uses web logs and a direct `PING` instead.
- Expected latency of failure was unknown; the playbook now records the
  ~10 s (reads) / ~27 s (writes) retry delay so responders do not mistake it
  for a slow network.
